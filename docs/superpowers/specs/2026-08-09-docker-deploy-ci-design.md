# Docker Deployment and GitHub CI — Design

**Date:** 2026-08-09
**Status:** Approved, ready for implementation planning

## Goal

Deploy Chinanki to an existing VPS as a Docker container behind the user's central Caddy
reverse proxy, and verify every push with GitHub Actions.

## Context

Chinanki is a local-only, offline-first PWA. It has **no backend, no database and no
server-side state** — every byte of user data lives in the browser's IndexedDB. Deployment
therefore means serving a directory of static files over HTTPS. The container is entirely
disposable: it can be deleted and recreated with no data loss, and needs no volumes.

Two properties of the app drive the design:

1. **It is a PWA, so it must be served over HTTPS.** Service workers do not register over
   plain HTTP, and without a service worker the app loses offline mode and installability —
   which is the entire point of the product. TLS is handled by the existing central Caddy.
2. **The dictionary is a 17 MB build artifact, not source.** `public/dict/` is gitignored
   and generated by downloading CC-CEDICT and sharding it. It must exist before `vite build`
   or hanzi auto-fill silently returns nothing.

## Existing infrastructure (fixed constraints)

The VPS runs a single central Caddy container at `/home/ubuntu/caddy` which owns ports
80/443 and obtains TLS certificates from Let's Encrypt. Application containers:

- **do not** publish ports to the host,
- **do not** run their own TLS or proxy,
- join the external Docker bridge network `web` with a network alias,
- are routed by a block added to `/home/ubuntu/caddy/Caddyfile`.

Existing examples: `pass.bourdet.be` → `vaultwarden:80`, `gripsou.bourdet.be` →
`backend:8080`, `roadia.bourdet.be` → path-split to `server:8080` / `client:3000`.

Chinanki follows the same shape: `chinanki.bourdet.be` → `chinanki:80`.

The VPS has 24 GB RAM, so building from source on the box is comfortable.

## Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Dictionary source | Downloaded during image build | Nothing extra in git; pinned by Docker layer cache, refreshed deliberately |
| Build location | On the VPS, from source | No registry auth to manage; ample RAM available; `--build` leaves the old container running if the build fails |
| Deploy trigger | Manual `./deploy.sh` over SSH | No SSH private key in GitHub secrets, no extra listener service, deploys happen when intended |
| Static server in container | Caddy | One config language across the stack; SPA fallback and cache headers in ~15 lines |
| CI scope | typecheck + unit tests + build, Playwright E2E, Docker build | Chosen by the user; no linter is added (none exists today) |
| Node version | `26.7`, pinned identically in Dockerfile and CI | Matches local dev exactly; Node is build-only here, so LTS buys nothing |

## Architecture

### Container

A two-stage Dockerfile. Stage one builds; stage two serves. Node and the intermediate
dictionary source never reach the final image, which lands around 60 MB.

```dockerfile
FROM node:26.7-alpine AS builder
WORKDIR /app

# Dictionary in its own early layer, so dependency churn does not re-trigger a 9 MB download.
ARG CEDICT_URL=https://www.mdbg.net/chinese/export/cedict/cedict_1_0_ts_utf-8_mdbg.txt.gz
RUN apk add --no-cache curl \
 && curl -fsSL "$CEDICT_URL" | gunzip > /tmp/cedict.u8

COPY package.json package-lock.json ./
RUN npm ci

COPY . .
RUN npm run build:dict -- /tmp/cedict.u8 \
 && test "$(ls -1 public/dict | wc -l)" -gt 100 \
 && npm run build

FROM caddy:2-alpine
COPY --from=builder /app/dist /srv
COPY docker/Caddyfile /etc/caddy/Caddyfile
EXPOSE 80
```

Two guards are load-bearing:

- **`curl -f`** — without it, a 404 or 5xx from mdbg.net produces an empty file, `build:dict`
  emits zero shards, and the image ships with auto-fill permanently broken and no error.
- **The shard-count assertion** — the sharding step must produce ~128 files. Asserting a
  floor turns a silent degradation into a failed build. `npm run build` also runs both
  typecheck passes, so a type error fails the image build too.

**Dictionary refresh.** Docker caches the `curl` layer by command string, not by remote
content, so the dictionary is effectively pinned until deliberately invalidated. To refresh:

```bash
docker compose build --build-arg CEDICT_URL="<url>#$(date +%F)"
```

This is the intended behaviour: reproducible builds by default, updates on purpose.

### Cache headers (`docker/Caddyfile`)

This is the part most likely to cause an unrecoverable production problem if wrong. An
over-cached `sw.js` or `index.html` pins users to a stale build with no remote way to fix it.

| Path | `Cache-Control` | Reason |
|---|---|---|
| `/assets/*` | `public, max-age=31536000, immutable` | Vite content-hashes these; safe forever |
| `/dict/*` | `public, max-age=604800` | Content-stable shards; worth caching hard |
| `sw.js`, `index.html`, `manifest.webmanifest` | `no-cache` | Unhashed filenames; must always revalidate |

```
:80 {
	root * /srv
	encode gzip zstd

	@immutable path /assets/*
	header @immutable Cache-Control "public, max-age=31536000, immutable"

	@dict path /dict/*
	header @dict Cache-Control "public, max-age=604800"

	@revalidate path /sw.js /index.html /manifest.webmanifest /registerSW.js
	header @revalidate Cache-Control "no-cache"

	try_files {path} /index.html
	file_server
}
```

`try_files {path} /index.html` provides the SPA fallback, so deep links such as
`/stats` survive a refresh. This replaces `public/_redirects`, which is Netlify-specific and
has no effect on this VPS. That file is deleted; the README's Netlify note is updated to
describe the Caddy setup instead.

### Compose

```yaml
services:
  chinanki:
    build: .
    image: chinanki:latest
    restart: unless-stopped
    expose: ["80"]
    networks:
      web:
        aliases: [chinanki]

networks:
  web:
    external: true
```

No `ports:` mapping — the container is reachable only from the `web` network, exactly like
the other services on the box.

### Central Caddy route

Added by hand once to `/home/ubuntu/caddy/Caddyfile`, then `caddy reload`:

```
chinanki.bourdet.be {
	reverse_proxy chinanki:80
}
```

### `.dockerignore`

Required, not optional. Without it `COPY . .` drags `node_modules/`, `dist/`, the host's
17 MB `public/dict/`, `.git/` and `test-results/` into the build context — slow, and the
copied `public/dict` would be overwritten by the build step anyway.

```
node_modules
dist
public/dict
.git
test-results
playwright-report
coverage
docs
```

## CI

One workflow, `.github/workflows/ci.yml`, triggered on push to any branch and on pull
requests. Three jobs run in parallel; a concurrency group cancels superseded runs on the
same ref.

| Job | Steps | Notes |
|---|---|---|
| `verify` | `npm ci`, `npm run typecheck`, `npm test`, `npm run build` | 279 tests; `actions/setup-node` with `cache: npm` |
| `e2e` | `npm ci`, `npx playwright install --with-deps chromium`, `npm run test:e2e` | Chromium cached by version key |
| `docker` | `docker/build-push-action` with `push: false` | BuildKit GHA cache for the dictionary and `npm ci` layers |

Notes:

- **CI does not need the dictionary.** The E2E smoke tests type words in manually, and
  `lookupPrefix` degrades to "no suggestions" when a shard is missing, so the `verify` and
  `e2e` jobs skip the 9 MB download entirely. Only the `docker` job builds it.
- **The `docker` job is the one that earns its keep.** Because the VPS builds from source, a
  broken Dockerfile would otherwise only surface mid-deploy, on the box, by hand.
- **Node `26.7` is pinned in both CI and the Dockerfile**, matching the local dev machine
  (`v26.7.0`), so all three environments run the same runtime. Node exists only in the build
  stage — the shipped image is `caddy:2-alpine` with no Node at all — so the usual argument
  for an LTS release (a long security-patch window at runtime) does not apply. The minor is
  pinned rather than floating `node:26-alpine`: this project has already been bitten once by
  unpinned toolchain drift, when TypeScript resolved to 7.0.2, dropped `baseUrl` support and
  broke the typecheck, forcing a pin to 5.9.3. Bump deliberately, in both files together.
- **CI is advisory, not gating.** Deploys are manual and nothing prevents deploying a red
  commit. Making it gate is a branch-protection setting on `main` — a GitHub configuration
  choice, deliberately out of scope for this repo.

## Deploy and rollback

`deploy.sh`, committed to the repo and run on the VPS:

```bash
#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")"
git pull --ff-only
docker image tag chinanki:latest chinanki:previous 2>/dev/null || true
docker compose up -d --build
docker image prune -f
```

- `--ff-only` fails loudly on diverged local state rather than silently merging.
- The retag before rebuilding preserves the last-known-good image.
- `docker compose up -d --build` builds *before* recreating, so a failed build leaves the
  running container untouched. Deploys fail safe.

`rollback.sh` restores the previous image in seconds rather than re-running a 3-minute build:

```bash
#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")"
docker image tag chinanki:previous chinanki:latest
docker compose up -d --no-build
```

## Verification

Docker and CI configuration cannot be unit-tested, so verification is a committed script,
`smoke-image.sh`, that builds and runs the image locally and asserts the things that
actually break in production:

1. `/` returns 200 and contains the app shell.
2. `/stats` (a client-side route with no file behind it) returns 200, not 404 — proves the
   SPA fallback works.
3. `index.html` and `sw.js` respond with `Cache-Control: no-cache`.
4. A file under `/assets/` responds with `immutable`.
5. A dictionary shard returns 200 and valid JSON — proves the dictionary was built and
   shipped. The script must discover an existing shard name rather than hardcoding one:
   shard keys are `codePoint % 128` in hex, so no specific filename is guaranteed to exist.

Run locally before the first deploy, and re-runnable after any change to the Dockerfile or
Caddyfile.

**Post-deploy check on the VPS:** load `https://chinanki.bourdet.be`, confirm the service
worker registers (DevTools → Application → Service Workers) and that the install prompt
appears. This is also the first real-hardware confirmation of installability and offline
behaviour, which the project has not yet had.

## Out of scope

- Image registry (GHCR) and pull-based deploys — reconsider only if VPS build time becomes
  annoying.
- Automated deploy from CI over SSH — rejected to avoid holding an SSH private key in GitHub
  secrets for a personal VPS.
- Watchtower or any auto-update daemon.
- Linting/formatting — no linter exists in this project today; adding one is separate work.
- Multi-architecture images — the VPS builds locally for its own architecture.
- Branch protection rules — a GitHub setting, not a repo artifact.

## Risks

| Risk | Severity | Mitigation |
|---|---|---|
| mdbg.net unreachable during a build | Medium | `curl -f` fails the build loudly; the running container is unaffected. Retry, or pass a `CEDICT_URL` pointing at a local copy. |
| Wrong cache headers pin users to a stale build | High | Explicit `no-cache` on all unhashed files; asserted by `smoke-image.sh`. |
| Dictionary silently empty | Medium | `curl -f` plus the shard-count assertion. |
| VPS build resource exhaustion | Low | 24 GB RAM; a Vite build wants ~1–2 GB. |
| CI green but VPS build fails | Low | The `docker` CI job builds the same Dockerfile; Node pinned to the same `26.7` in both, matching local dev. |
| Node 26 is a Current release, not LTS | Low | Node is build-stage only; no Node ships in the runtime image. If a future Node breaks the build, the pin means it breaks on a deliberate bump, not spontaneously. |
